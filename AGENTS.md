# TurboSuperMemory Agent Notes

## Toolchain And Shell

- This is a Rust 2021 workspace with six crates. The toolchain is pinned in `rust-toolchain.toml` (stable 1.99.0 with `rustfmt` and `clippy`) so the `-D warnings` clippy gate sees the same lint set everywhere; bump it deliberately and fix new lints in the same change. The PyO3 extension uses `abi3-py312`.
- Python extension and evaluation work must use Python 3.12. Set both `PYO3_PYTHON` and `PYTHON` when overriding the interpreter; the Windows Makefile default is the machine-specific `C:\Users\User\AppData\Local\Programs\Python\Python312\python.exe`.
- Make recipes use POSIX `export`, `cp`, and `rm` even on Windows. Run them under GNU Make with a POSIX shell (for example Git Bash/MSYS), not `nmake` or a PowerShell-only shell.
- Building `turbomemory_api` runs `tonic-build` over `crates/turbomemory_api/proto/turbomemory.proto`; `protoc` must be installed and on `PATH`.
- CUDA is opt-in: `make build-python FEATURES=cuda`. The feature propagates from `turbomemory_python` through storage to `turbomemory_gpu`; the normal build always uses the CPU fallback.
- `.cargo/config.toml` only carries the macOS linker flags a plain `cargo build` of the extension needs (`-undefined dynamic_lookup`); it does nothing on Linux or Windows.

## Workspace Boundaries

- `turbomemory_core`: vector math, SIMD/FWHT, quantizers, quantized scoring, and the token-budget packer (`packing.rs`). Keep I/O and persistence out.
- `turbomemory_graph`: BM25, concept extraction, graph/reinforcement/belief semantics, the bounded one-pass graph expansion (`SpreadingActivation`), and CCS/compressors. There is no Feeling-of-Knowing gate and no lateral inhibition; both were removed from the query path (`docs/cognitive_graph.md`).
- `turbomemory_gpu`: the `GpuBackend` abstraction, CPU fallback, and optional CUDA implementation. The engine uses two of its paths: exact search over device-resident vectors (`resident_*`, driven by `turbomemory_storage/src/gpu_exact.rs`) and, when that is off, the batched `gemm` rerank behind `search_ann_batch`. There is no GPU index build or GPU index search.
- `turbomemory_storage`: the central `StorageEngine`, persistence, indexes, tier lifecycle, filtering, and background workers. Start at `engine/mod.rs` (the struct, `open`, the consolidation cycle, `flush`/`shutdown`); its methods are grouped by concern in `engine/{write,search,retention,belief}.rs` and its unit tests live in `engine/tests.rs`. Tier decisions live in `config.rs`, `segment_holder.rs`, and `optimizer.rs`.
- `turbomemory_python`: the `MemoryEngine` PyO3 facade. Keep it thin and preserve `py.allow_threads(...)` around heavy engine calls and zero-copy contiguous `float32` NumPy paths.
- `tsm/` (Python): the shipped SDK. `memory.py` is the `Memory` facade.
  - The engine-free logic is imported by the eval harness (`benchmarks/cognitive_eval`) too, so evaluations measure shipped code: `budget.py`, `compaction.py`, `gist.py`, `concepts.py`, `ranking.py`, `reading.py`, `sources.py` (facts as keys, their source turns as what is read), `when.py` (rule-based resolution of relative dates against the date said) and `answering.py` (the reading prompt with deterministic tools).
  - `answering.py` is the only one of these that calls a model, through a client the caller passes.
  - Packaged with the extension by maturin (`pyproject.toml`).
- `turbomemory_api`: shared behavior belongs in `service.rs`; transport conversion belongs in `grpc.rs`/`rest.rs`. Edit the proto source, never generated files under `target/`.

## Required Verification

- For local iteration, run the narrow crate/test first, then format check, clippy, and the Rust suite.
- For storage-engine or cognitive-layer changes, finish with `make gate`; use `make gate GATE_ARGS=--quick` only for a faster, noisier pass. The gate rebuilds the extension and runs formatting, clippy, Rust tests, the `tsm` SDK unit suite, synthetic belief checks, a role-filtered LongMemEval smoke test, and an ANN recall floor.
- `make gate` must run under Python 3.12 and expects the LongMemEval data (download it with `make download-eval-data` — the datasets are too large to check in, so a fresh clone has none until downloaded) plus a locally cached embedding model (`sentence-transformers/all-MiniLM-L6-v2` in the Hugging Face cache) to be usable offline (`HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`).
- Full cognitive evaluations and performance benchmarks are expensive and are not substitutes for the regression gate. Their runners and prerequisites are documented in `benchmarks/cognitive_eval/README.md` and `setup.sh`.
- Before paying a judge for a retrieval change, use the free score: `python benchmarks/cognitive_eval/shipped_stack_eval.py --offline --limit 120 --arms sdk_pack_tagged,sdk_cognitive --config NAME:KEY=VALUE` prints, per arm, for how many questions the turns the dataset marks as evidence are all in the context (needs `download.py --official oracle`; two minutes, no network). Check a ranking change on `--pool 20` and `--pool 40` as well: those build one history from many conversations, so most of the store is distractors and it passes the 4,096-record line where search stops being an exact scan. The score says nothing about what a reader does with the context (time tags, the question date), which still needs a judged run. The LongMemEval copy the harness downloads by default is the benchmark's oracle variant (evidence sessions only); `--variant s` is the standard one and needs its histories extracted first.
- Judged runs worth knowing about (`shipped_stack_eval.py`, 2026-10-21):
  - `full_context` is the no-memory control: every message of the history, dated, with no budget.
  - `--skip 120 --limit 500` runs the 355 held-out questions that no setting was chosen on. The extraction cache covers them, so only the judge is paid.
  - `--recall NAME:KEY=VALUE` adds an arm `rcl_NAME`, which reads the `sdk_cognitive` store with those `recall()` arguments. Identical contexts share a verdict, so a read-time change costs only the questions it changes.
  - `--reader tools` asks with `tsm.answering`.
  - Paid results go to `$TSM_EVAL_DIR`, by default `~/.tsm_eval/shipped_stack_eval`, outside the checkout. That covers verdicts, gists, the embedding overlay, and the run files you write there with `--out`. They used to live under `target/` and then `.cache/`, and each was wiped once, taking every saved verdict with it. Pass `--out "$TSM_EVAL_DIR/runs/NAME.json"` so a run can be paired later with `benchmarks/cognitive_eval/pair_runs.py`.
  - `benchmarks/cognitive_eval/prefetch_extraction.py` extracts many histories in parallel into the runner's cache (LongMemEval-S: about 480 messages a question). Run it with `--dry` first, which prints the request count.
  - To measure the committed code while `tsm/` is being edited, run it from a worktree of `HEAD` (e.g. `git worktree add --detach .cache/eval_tree HEAD`).
  - A run stops when the OpenAI account is out of credit (`tsm._retry.QuotaExhausted`). Finished histories stay in the checkpoint, and verdicts are saved. It used to carry on with pairs left unverified.
- There is no CI. The workflow was removed on 2026-10-21, so `make gate`, run locally, is the only check. Nothing builds or tests Linux or macOS any more. The AArch64 NEON kernels are only type-checked by the clippy command above; the macOS job that compiled and ran them is gone.
- AArch64 compiles different code in `turbomemory_core/src/metrics.rs` (NEON kernels, no scalar fallback). After touching it, lint that target too: `rustup target add aarch64-unknown-linux-gnu && cargo clippy -p turbomemory_core -p turbomemory_graph --all-targets --target aarch64-unknown-linux-gnu --target-dir target/aarch64 -- -D warnings`.
- `crates/turbomemory_storage/tests/robustness.rs` pins failures that were reproduced against the engine (writes lost on an unclean stop, a store that broke in a later session, cross-scope results, process-killing inputs, hangs under concurrent use). Extend it when fixing a bug of that kind. Two rules it relies on: a crash test must drop the engine WITHOUT calling `flush`/`flush_vectors` first (flushing stamps the vector-file header and hides recovery bugs), and tiered-path tests need more than 4,096 records (below that every search takes the exact scan).
- The CUDA build is not part of the gate. After touching `segment_holder.rs`, `gpu_exact.rs`, `engine/search.rs` or `turbomemory_gpu`, also run `cargo test -p turbomemory_gpu -p turbomemory_storage --features cuda --target-dir target/cuda` on a machine with a GPU. The `resident_search_*` robustness tests force the resident path for a store of any size (`gpu_exact_on_cpu_backend`, `gpu_exact_min_records = 0`): without the feature they run it on the host backend, with it on the device, where `batch_search_matches_single_search_on_a_tiered_store` exercises the rerank too. `benchmarks/gpu_parity.py` compares builds from Python.

## Engine Invariants

- `StorageEngine::open` returns `Arc<StorageEngine>` and the engine owns its synchronization. Do not add an external mutex around it; clones share internal `Arc`s.
- `shutdown()` stops the background optimizer, then flushes; the database lock, mmaps, and index files are released when the last `Arc` drops. Python `MemoryEngine.close()` does both (it takes the engine out and drops it), so the same path can be reopened immediately and any later call raises `RuntimeError`. Do not go back to a flush-only `close()`.
- The engine is the only store for the SDK: `tsm.Memory` reads text/role/scope back with `get_records` and mints ids from `next_insert_seq` (durable, never reused). Do not reintroduce per-process id/text/role maps; a reopened database must behave like the one that was written.
- Durability order is vector mmap write, metadata-only WAL append, then lazy `redb` snapshot. With `TierConfig::sync_writes` each write also syncs its vector range and then its WAL record before returning (vectors first: a synced log record whose vector is not on disk would be dropped by recovery); new files and manifests fsync their directory on POSIX (`sync_dir`). `flush()` drains pending seals/access counters, syncs vectors/text/metadata/segments/graph/CCS, and only then clears the WAL. Preserve this order and cover persistence changes with restart/crash tests. A segment build that fails during `flush()` does not stop the durable part: the error is returned after everything else is on disk.
- Recovery must not depend on a clean stop. The vector file's header count is only stamped by `flush`, so WAL replay never uses `VectorStore::get` (which stops at that count): each WAL insert carries a CRC of its vector and replay reads the slot itself with `VectorStore::recover`. An update is one `WalOp::Replace` record, never a delete followed by an insert. A torn or corrupt WAL tail is cut at the last good frame (`Wal::truncate_to`), never fatal. `StorageEngine::recovery_report()` (Python: `recovery_report()`) says what an open had to repair.
- Every write validates all of its input before changing anything (`engine/write.rs::prepare`: non-empty id, dimension, finite non-zero vector, finite importance, payload JSON), then commits under `write_lock`. A rejected insert, batch, or update leaves the store exactly as it was; a batch is all-or-nothing.
- Segment directories are derived data and are named by a counter that continues past every directory already on disk (never restart it at zero). A segment's manifest is written last, atomically (`segments::write_manifest_atomic`); a directory without one is an abandoned build and is removed on open. A segment that fails to load is discarded and its records re-indexed, never a failed open. usearch index files are checked against the length and CRC in their manifest before being mapped, because the native library reads a truncated file out of bounds.
- What is NOT derived is reported, not papered over: `open` returns `StorageError::Corrupted` when `vectors.bin` or `memory.redb` is missing, truncated, or inconsistent with the other.
- Full embeddings live in `vectors.bin`; `MetaRecord`/WAL/redb metadata must not duplicate them. Derived id, scope, payload, text, graph, and segment indexes are rebuilt or reloaded on open. Graph snapshots are stored binary (`meta_bin` table, `TMGR` magic) with legacy JSON snapshots still readable on open; the next flush rewrites them as binary.
- Search uses an exact scan at 4,096 records or fewer. Above that, a CUDA build with a usable device answers from the vectors mirrored in device memory (`gpu_exact.rs`, exact, see the GPU invariant below); otherwise immutable segment snapshots search Hot/SealedHot/Warm/Cold candidates and rerank against full-f32 vectors. Both exact paths end in `finish_exact`, which orders ties by offset and widens the head when superseded or just-deleted records took slots. Immutable segments keep the offsets of deleted/updated/evicted records, so the tiered path filters them out and searches again with a wider pool until `top_k` live results are found (`engine/search.rs::live_top_k`); do not go back to filtering after the cut.
- Queries are validated (`validate_query`: dimension and finite) and `top_k` is clamped to the record count before it can size anything. Sort scores with `turbomemory_core::cmp_score_desc`, not `partial_cmp(..).unwrap_or(Equal)`: the latter is not a total order with a NaN present and the standard sort may panic.
- A scope or payload filter bounds every stage of a search. The concept graph and the BM25 index are shared by all scopes, so cognitive search passes the restriction into the expansion (`SpreadingActivation::search_restricted`) and re-checks each candidate in `hydrate_and_fuse`. Deduplication only merges records of one scope, and `commit_supersessions_by_id` rejects cross-scope and self pairs. Still shared by design: the `max_records` cap, importance normalization, vocabulary evolution, and `step_session`'s working memory.
- Never hold the vector-store read view (`read_view()`) across a wait on the Rayon pool or take it twice on one thread: a queued writer blocks new readers, and the pool's workers are readers. `cpu_rerank_candidates` is sequential for this reason.
- usearch gives each index a fixed number of search contexts and fails a search when none is free; `UsearchIndex` gates searches with a semaphore so extra callers wait.
- Hot sealing only swaps the mutable segment into a pending queue. The optimizer later chooses HNSW SealedHot or quantized Warm based on thresholds/resource budget; Warm compacts to Cold after `warm_capacity`.
- Default Warm and Cold quantizers are both scalar 8-bit. TurboQuant variants require a power-of-two dimension, so they are invalid with the default dimension 768 and must return `InvalidArgument`, not panic.
- Belief revision, abstraction, auto-importance, vocabulary evolution, eviction, and deduplication are opt-in. Do not assume the README's cognitive examples are default behavior.
- Cognitive `search` returns `None` when nothing within the query's scope/filter matched (no ANN seeds). Nothing gates a query on confidence; the API's `gated` flag only reports that empty case.
- A search is a read. It does not reinforce graph edges unless `reinforce_on_search` is set (it did once, and the same question then came back as a different list the second time); `StorageEngine::reinforce` is for memories a caller says were used. Access counters are still bumped.
- The augmenter never drops an ANN seed: at its cut (`SpreadingActivation::search_restricted`, step 4) every seed is kept and only the graph-discovered candidates compete for what is left. Ranking both kinds together by cosine + delta let word matches crowd true neighbours out once a store held a few thousand memories. Before that cut the expansion walks every seed and keeps the `expansion_max_candidates` strongest graph candidates; it used to stop at the cap, so later seeds were never expanded and what was kept depended on edge order.
- The graph boost has two scales. `cognitive_alpha` adds a fixed amount (up to `1 - alpha`); `graph_weight` adds a share of the cosine spread among the `top_k` nearest candidates and takes precedence when set. The fixed form at 0.5 is about eighteen times the cosine gap between neighbouring candidates on OpenAI embeddings and ranked by word overlap; do not use it as a default for a new profile without measuring. `query_concept_boost` (the per-word concept bonus), `fan_exponent` (fan normalization) and `max_concept_share` (hub pruning: a concept attached to more than that share of all memories is not walked through; it changed no context at 0.15 or 0.30, 2026-10-28) are separate `SpreadingConfig` knobs whose defaults keep the original behaviour.
- `GistCompressor::compress` has three outcomes: `Ok(Some)` stores the gist and the victims are deleted, `Ok(None)` is an abstention (victims deleted without a gist), `Err` is a failure and the victims are kept for the next eviction. Do not collapse failure into abstention: that deletes memories with nothing in their place.
- GPU failures deliberately fall back to CPU. With the `cuda` feature, vector search runs on the device mirror: row `i` is the vector at offset `i`, kept current by uploading the tail written since the last search. That relies on two facts that must stay true: offsets are allocated in increasing order and never reused within an engine's lifetime, and a vector is never rewritten in place (an update writes a new offset). Deleted, updated and filtered rows are masked on the host from the payload index's live set, never on the device. Queries are scaled to unit length so scores stay cosines. A store that outgrows `gpu_memory_budget_mb`, or any device error, switches the mirror off for the life of the engine (`GpuExactIndex::settle`) and it must not be re-created by a search that was already queued. Free a mirror through `GpuBackend::resident_release`, not by dropping it: cudarc frees into the device's memory pool, which keeps the memory reserved for the process until the stream is next synchronized, so a closed engine would go on holding it. Segments are still built in a CUDA build: they are the fallback. HNSW construction and search and the quantized-tier scan run on the CPU.
- Release builds unwind on panic (`panic = "unwind"`). The engine runs inside other processes; with `abort` any panic killed the Python host or the whole server.

## Change Routing

- Distance/SIMD/FWHT/quantization: `crates/turbomemory_core/src/{metrics,quantization,turbo_quant,metrics_quantized}.rs`.
- Retrieval, durability, filtering, or concurrency: `crates/turbomemory_storage/src/engine/{mod,write,search}.rs` plus the relevant index/store module.
- Tier lifecycle/HNSW: `crates/turbomemory_storage/src/{segment_holder,optimizer}.rs` and `src/segments/`.
- Cognitive behavior: `crates/turbomemory_graph/src/{activation,graph,extract,ccs}.rs`; belief orchestration lives in `crates/turbomemory_storage/src/engine/belief.rs`, and eviction, gist-before-evict, dedup, and importance scoring in `engine/retention.rs`.
- Public Python behavior: `crates/turbomemory_python/src/lib.rs`; preserve storage-to-Python exception mapping (`ValueError` for invalid/duplicate/dimension/zero or non-finite vectors, `KeyError` for missing ids, `RuntimeError` otherwise, including a corrupted store). The engine handle sits behind a mutex and every method works on its own `Arc` clone, so `close()` takes `&self`; Python callbacks are held as bare `Py<PyAny>` (no lock around the call, which deadlocked against the GIL).
- SDK backends (`tsm/extractors.py`, `tsm/embedders.py`, `tsm/gist.py`) share `tsm/_retry.py`: transient errors back off and retry, HTTP 400/401/403/404/413/422 fail at once, and error messages never repeat the provider's text. The extractor must never turn a failed extraction into "no facts": a cut-off or malformed reply is retried with a larger budget and then falls back to the message itself, uncached. A well-formed empty reply is a separate case: the first prompt returns nothing for a third of user messages (mostly a statement about the user followed by a request). Two opt-in steps recover such a message of three words or more, both `False` by default in `OpenAIExtractor` and not set by `Memory`: `second_look` asks it again with a second prompt (what the speaker reveals, including inside a question), and `keep_unextracted` then stores its sentences that are not questions as said (`statements`, about 80 tokens a piece). They are off because they did not pay when judged (below); turning them on by default waits for the paired store x budget x reader grid in `TODO.md`. Keep the first prompt first: asking every message with the second one cost judged answers (79 of 115 against 90 at 150 tokens). Do not read the evidence score as answers here: the second pass took it from 76 to 92 questions at 150 tokens while judged answers with the plain reader went from 90 to 82; at 600 tokens they went from 86 to 92, and to 99 with the `tsm.reading` prompt (`benchmarks/PHASE_PROGRESS.md`, 2026-10-12). Both prompts are cached under a hash of their text, so editing one re-extracts (paid) instead of serving replies to the old one. The embedding cache is loaded with a restricted unpickler (arrays only); do not replace it with a plain `pickle.load`. `tsm/tests/test_backends.py` covers these with fake clients.
- Embedders and database identity: `tsm/embedders.py`, `tsm/identity.py`, `tsm/interfaces.py`. `Memory` embeds a question with `embed_query` and everything it stores or compares with stored text (facts, gists, the packer's redundancy check) with `embed_documents`; both fall back to `encode`, so call neither `encode` directly nor assume one vector per text. A database records its embedder's `fingerprint` in `tsm_embedder.json` (SDK-side, written atomically; the engine knows only a dimension) and refuses another with `EmbedderMismatchError`, because two models of one dimension return wrong results without an error; an empty database takes any embedder, one with no record adopts the first that opens it. The fallback fingerprint is the class name and the dimension, never the module: the module is `__main__` in a script and a package path when imported, which made one embedder look like two (a subprocess test caught it). Re-embedding in place is not an option (`update` allocates a new insert sequence, which belief revision orders old against new by): changing models means re-ingesting. `SentenceTransformerEmbedder` applies per-model card settings by name (`_MODEL_DEFAULTS`): EmbeddingGemma 2 loads its text model only (271M parameters, about 0.5 GB in bfloat16), is bounded at its 8,192-token context (sentence-transformers reports no limit), and refuses float16 (NaN, no error); a load-time probe checks for finite vectors of the declared size, and calls are serialized because HF tokenizers raise `Already borrowed` across threads. Cosine thresholds belong to an embedder's geometry, not to the profile: the conversational profile's belief thresholds (0.85 / 0.75) are tuned on OpenAI vectors, and with EmbeddingGemma 2's they flag 30 of 58 still-true pairs stale and cost 10 of 77 questions their evidence (p = 0.012). An embedder may declare `engine_defaults` (applied over the profile, under explicit `Memory(...)` arguments; Gemma: 0.92 / 0.86); any new embedder needs `belief_pairs_eval.py --embed-model ...` and the `sdk_belief` arm run before the profile is trusted with it. Results with it, MiniLM and the OpenAI vectors on the free evidence score are in `benchmarks/PHASE_PROGRESS.md` (2026-10-19). sentence-transformers 6.1 is the floor for it (`tsm[gemma]`) and 6.0 for the ColBERT reranker (`tsm[colbert]`); the `cpu`/`cuda` extras keep 2.2 for MiniLM.
- Idle consolidation: `Memory(idle_consolidation_secs=N)` starts a daemon thread (`_idle_loop`) that runs `consolidate()`, the whole verified flow, after N seconds without `add()` / `recall()` when something was written since the last pass (or the store had memories when opened). One pass at a time (`_maintenance_lock`, a manual `consolidate()` waits); a pass is never interrupted, because a verifier request cannot be; a failed pass or `verifier.unresolved > 0` is retried after another idle period (at least `IDLE_RETRY_FLOOR_SECS`), nothing is deleted on failure, and `close()` joins the thread (up to `IDLE_CLOSE_TIMEOUT_SECS`) before it takes the engine out. It is not the engine's `auto_consolidation_secs`, which has no verifier and which the conversational profile keeps at 0. Off by default.
- Belief revision in the SDK: `Memory.consolidate()` proposes, the verifier vets, accepted pairs are committed. A superseded fact is never dropped from recall by default (no profile sets `exclude_superseded`; removing them lost judged answers about the past): it is demoted and flagged (`superseded_by`). Only with a verifier does `recall()` act on the flag in what a model reads: `context` gets `STALE_MARK` and the current belief is ranked where the old one would have been without its demotion (`resolve_beliefs` reports the factor) and added if the search missed it. Unverified flags stay metadata, because unverified detection marks true facts stale too often. The demotion (`supersession_demotion_factor`, 0.4) keeps a marked fact out of a small context almost always; without it (1.0) judged answers came out level, so the default was left alone. `select_under_budget` never treats a fact and the one it replaced as duplicates. A verifier with a `candidate_min_cosine` attribute (`tsm.verification.LLMVerifier`) is given the engine's wide candidates (`propose_supersession_candidates`: no lexical gates, so never commit them unvetted; each memory is offered only its closest older memory and those within `margin` of it, and that closest one stays the reference after it has been replaced, so repeated cycles do not work their way down the neighbour list); any other verifier gets `propose_supersessions`. `benchmarks/cognitive_eval/belief_pairs_eval.py` scores a setup against 260 labeled pairs (tune on `--split dev`, quote `--split test`); a change to detection, the verifier prompt or these defaults needs a run of it and a note in `benchmarks/PHASE_PROGRESS.md`. Two rewordings for repeat occurrences and different subjects scored at or below the shipped prompt on `--split dev` (2026-10-21) and were not adopted: gpt-4o-mini's errors move between pairs with any rewording, so judge a prompt change on both layouts before reading anything into one or two pairs.
- Per-user storage budget: `Memory(max_user_tokens=...)` and `tsm/compaction.py::plan_compaction` (newest facts kept, user's first; the rest and every earlier gist folded into short gists; superseded facts folded first). `benchmarks/cognitive_eval/budgeting.py` builds its role-aware store with the same function, so the bounded head-to-head measures it. Gists are inserted before the folded memories are deleted and a summarizer failure removes nothing; keep both. Gists are stored under the roles `summary` / `summary-assistant`, which the role prior treats like the roles they summarize, and each gets a `turn_index` of its own; without either the packer passes them over. The engine's `max_records` eviction is separate (store-wide, by count, newest or most-used first) and scored far lower on the same questions.
- SDK behavior: `tsm/memory.py` plus the shared modules above. `recall()` returns results sorted by the returned score and fills a token budget (there is no default item cap any more: a fixed cap left half of a 150-token budget unused and cost judged answers). A result's `context` is what a model should read, in this order:
  - `time_tag`: the message's date, else `[turn N]`. A gist gets `span_tag`, the dates of what it summarizes, kept in its payload by `plan_compaction(spans=...)`. Tags count against the budget. They are on by default because they gained judged answers on temporal questions; `time_tags="minute"` adds the time of day.
  - With a verifier, `stale_mark`: `[earlier, changed by DATE]`, where DATE is when its replacement was said (`valid_until`), else `STALE_MARK`.
  - The text.

  The dated stale mark and gist spans were added 2026-10-21 and judged level on 2026-10-28 (98 / 97 and 96 / 98 of 115), so both stay on. `Memory(compaction="merge_oldest")` scored 57 against 50 for the default rolling compaction (p = 0.23, `benchmarks/PHASE_PROGRESS.md`); the default stays `"refold"` until a held-out run decides it.

  Every result also carries `source`, the message it was extracted from. Two read-time options are opt-in and were measured on 2026-10-21:
  - `sources="turn"` (`tsm/sources.py`): turns lost at 600 tokens, 86 against 98.
  - `event_dates=True` (`tsm/when.py`): level, 8 gained and 4 lost over 470 questions. `recall()` is a read and reinforces nothing; `Memory.reinforce(ids)` is the explicit form. The conversational profile ranks with `graph_weight=0.5`, `query_concept_boost=0.0`, `fan_exponent=1.0` (an explicit `cognitive_alpha` passed to `Memory()` removes the profile's `graph_weight` so the fixed boost applies). The role prior (user x1.30, assistant x0.85 for the broad `FIRST_PERSON_CUES`) is not applied to a question about what the assistant said (`tsm.ranking.asks_what_assistant_said`: past-tense cues, 54 of the 56 single-session-assistant LongMemEval questions and no other type). With the prior, those questions found their evidence 3 times in 11 on a LongMemEval-S slice; without it, 10 (2026-10-29). The prior never damps the `PRIOR_SPARES_TOP` (3) best-scored candidates, and a counting question (`is_counting_query`: "how many", "how much", "total") packs with `lam` 0.9 instead of 0.7 (`packing_lam`). `recall()` and the harness's plain arms both go through `apply_role_prior` / `packing_lam`, so keep them there. For such a question, `recall()` also returns the two best-scored assistant replies in the context whole: their passages are joined in order, read by consecutive id within the `passages` count stored with each, and capped at `REPLY_SHARE` of the budget (`_whole_reply`). That took those questions from 7 to 11 of 11 judged. `MAX_REDUNDANCY` in `tsm/budget.py` is 0.95: it skips near-identical text only, because memories that merely read alike are often the separate instances a question needs (at 0.72 it cost 7 of 115 questions their full evidence). `select_under_budget`, the role prior, concept extraction, and the gist summarizers feed the published eval numbers; a behavior change there needs a gate run and a note in `benchmarks/PHASE_PROGRESS.md`.

  A budgeted `recall()` packs in the engine (`MemoryEngine.pack_under_budget` -> `StorageEngine::pack_under_budget` -> `turbomemory_core::packing::select_under_budget`) on the vectors it already stores, so it embeds only the question. The Python packer embedded every candidate again: 250 texts a recall at 2,000 tokens. Both packers make the same greedy MMR choice and must stay in step (`MAX_REDUNDANCY`, `NEW_TURN_BONUS`, `GAIN_TIE`, the replaced/replacement exemption, and occasions: two message passages said on different days, `tsm.chunks.occasion`, are never skipped as near-duplicates of each other, only weighed as redundant); `TestEnginePacker` checks that they agree. `GAIN_TIE` (1e-6) exists because numpy and the Rust dot product round a cosine differently in its last bit, which split exact ties differently. `sources="turn"` still uses the Python packer, because a turn is not a stored record.

  `Memory(keep_messages=True)` also stores every message as said, cut by `tsm/chunks.py` into passages of at most `PASSAGE_TOKENS` (100), each a record under the role `message` / `message-<role>`. Belief revision (`belief_source_roles=["user"]`) leaves them alone. The role prior ranks them like their speaker, and `recall()` shows them as `[date] user: ...`. Passages never part a list number from its item: a sentence-final number counts as one only in a run of consecutive numbers that starts at 1 or is `LIST_RUN` long. `extractor="none"` stores only the passages, so `add()` asks no model. It is on by default (`keep_messages=None`) unless `max_user_tokens` is set, which it refuses, because compaction folds by speaker and does not know passages. Judged on the first 30 LongMemEval-S histories (29 questions, `--reader notes`, 2026-10-29), facts alone answered 19 / 20 / 19 at 600 / 1,200 / 2,000 tokens: extraction is their ceiling. Facts plus messages answered 23 / 25 / 27 (8 / 0 at 2,000, p = 0.01), and messages alone 22 / 24 / 26. Harness arms store the facts alone unless they name the messages (`sdk_memory` pins `keep_messages=False`); so do the SDK tests that are about facts (`make_memory`).
- Answering from recalled memories: `tsm/reading.py` builds the prompt (`answer_prompt`: the memories in the order they were said, then the model lists what bears on the question, settles what changed and what has to be counted or computed, and ends with one `Answer:` line) and `final_answer` takes the answer out of the reply; nothing there calls a model. The harness asks with it under `--reader notes`. On the 355 held-out questions it answered 296 at 600 tokens, where the plain prompt at 150 answered 259 (52 gained, 15 lost; 2026-10-21). On the 115 dev questions the raw evidence sessions, read with the same prompt, answered 104 and memory 98, so on the oracle file the memory layer costs about six questions (p = 0.24). `tsm/answering.py` is the same prompt with deterministic tools (arithmetic, dates, distinct counts). It scored 94 against 98 and is not the harness default. The free evidence score cannot see a reader, so a change to `ANSWER_SYSTEM` needs a judged run. Give the model about 800 reply tokens: a reply cut off before its last line has no answer in it.
- Public server behavior: `crates/turbomemory_api/proto/turbomemory.proto` plus `src/{service,grpc,rest}.rs`. The server starts gRPC and REST together with graceful shutdown (Ctrl-C, SIGTERM, or one server's failure stops both, then the engine is flushed); defaults come from `TURBO_DB_PATH`, `TURBO_DIMENSION`, `TURBO_GRPC_ADDR`, `TURBO_REST_ADDR`, `TURBO_FLUSH_INTERVAL_SECS` (background flush, default 30 s, `0` disables), and `TURBO_SYNC_WRITES` (`1` syncs every write to disk before acknowledging it) in `main.rs`. The service opens the engine without its optimizer thread, so that periodic flush is the only thing that fsyncs, truncates the WAL, and builds index segments while the server runs. Setting `TURBO_API_KEY` enables bearer-token auth on both transports; unset means open access (a wildcard bind logs a warning). REST errors are JSON (`{"error":{code,message}}`), the JSON filter DSL caps nesting at `MAX_FILTER_DEPTH = 32`, and batch inserts validate parallel-array lengths.
